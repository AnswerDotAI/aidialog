Overview

dlg2hist converts a dialog into alternating user turns and AI reply strings. It accepts a Dialog or an iterable of messages, plus a model-capability dictionary. Each user turn contains the prompt and any preceding notes, code, and media. Hosts use this history as input to a model.

Message.hist_xml formats one message as XML. Message.to_media collects its media. Message.to_parts combines both into the list of text and media items for history.

For structured chat messages, use dlg2chat. It recovers tool calls and results from the stored replies. chat2dlg converts those messages back into a dialog. To edit the contents of a single reply, use reply2dlg and dlg2reply.

Media

A model needs both the media and enough context to identify it. We put an XML <media> tag immediately before each media item. The tag records its id, type, and mime.

The ID identifies the source:

  • An attachment uses its UUID from the Markdown attachment:uuid reference.
  • A variable uses its name.
  • A code output image uses a content hash.

The type attribute describes where the media came from. output means a code cell output. variable means a variable value. content means media embedded in the message’s Markdown.

Media context tags

media_item accepts bytes, a MediaUrl, or a function that loads either. It checks the MIME type against the model’s capabilities before preparing the data. Successful results contain the <media> tag followed by the data.

The capability flags are supports_vision, supports_video_input, supports_pdf_input, and supports_audio_input. A missing flag means no support for that media type. The unsupported-media message asks the user to choose a model that supports it.

Expected failures return a <media-unavailable> tag. These include missing files, invalid base64, and unavailable or unsupported data. The tag records the reason and tells the model to inform the user that it cannot see the media. Image preparation and a host’s path checks can also report these failures. Unexpected exceptions still propagate.

PDF token estimates use a page count. pdf_pages reads /Count values from /Pages nodes without a PDF library. In a complete page tree, the root holds the total and no child has a larger count. The function takes the largest count it finds.

PDF 1.5 permits these nodes inside compressed object streams. pdf_pages uses zlib to inspect those streams too. An incremental edit that removes pages can leave an older, larger root in the file. Counting that root overestimates the token budget rather than underestimating it. This is a heuristic, not a complete PDF parser. It returns zero when it finds no matching count.

Use output_parts when a host needs to send code output images to a model. Solveit uses it for tool results. The same function can prepare media for an MCP frontend. It checks model support, resizes images, and adds their ID tags. It returns Part objects, including unavailable-media notices for expected failures. Images are enabled when aim_info is None.

merge_media combines these parts with the rendered output text. If the parts include an image, it returns a list. Each media tag stays next to its image, with the output text last. Without an image, it returns a plain string containing the output text followed by any unavailable-media notices. Callers use this return type to distinguish text-only results from multipart results.

Static media refs

Add #ai to a Markdown image target to include it in model context: ![alt](ref#ai). The model doesn’t see media from links without this suffix.

The target can be an http:// or https:// URL, a data: URL, or a file path. Web URLs use a lazy MediaUrl. Data URLs decode inline. Dialog.media_path resolves file paths.

Hosts patch media_path to apply their own directories and safety rules. Solveit uses it to map /static/ and restrict production access to its data directory.

Sigil refs and variables

Prompts can refer to kernel values, tools, and shell output with a character before a backtick expression:

  • $`expr` requests the value of a kernel expression.
  • &`tool` activates a tool.
  • !`cmd` requests shell output in hosts that provide a shell.

This module parses the references. The host evaluates them because it owns the kernel, toolset, and shell.

get_refs parses names for the & form. It accepts a single name or a list such as &`[python, bash]`. sigil_pat handles $ and !. Their backtick content can be an expression or command, rather than a name.

get_exprs collects references from prompt content. expr_mtypes defines the participating message types. Notes, code, and outputs don’t request interpolation, even when they contain the same syntax. Pass sigil='!' to collect shell references instead of kernel expressions. Parsing doesn’t evaluate either kind of reference.

Hosts evaluate references in their kernels with ipyfuncs’ eval_exprs, usually through a client helper. Each requested expression has a result. Evaluation failures return an <error> element as a string instead of omitting the key. Its type attribute identifies the exception.

is_nameerr recognizes the NameError marker. Hosts use it to warn about missing variables rather than show the error as a variable value. Other errors remain visible in the values. This distinguishes a missing name from a reference whose evaluation failed.

Message XML Helpers

Message.hist_xml formats notes, code, and other non-prompt messages with item2xml. The tag names the message type and contains the content directly. An <out> section contains any output. This history rendering includes time information. Message.to_xml provides the concise rendering used by dlgskill.

Prompts use prompt_txt instead. The AI reply belongs to the next history turn, not inside the prompt XML.

The prompt envelope

A user turn can contain notes, code, and media before the prompt. task_tags separates the actual request from that context. It returns an <instructions> element followed by a <prompt> element containing the request.

The prompt’s sid identifies the message for tools. Its time records the local run time when available. prompt_txt uses the dialog’s timezone, or UTC without one.

Hosts can add warnings alongside the live prompt. warning_tag puts these in a <system-reminder> element. Examples include undefined variables and context-budget trims.

Convert dlg to LLM history. The final prompt renders with last=True.

Dialogs to canonical messages

dlg2chat converts a dialog into the canonical Msg format used for provider conversions and transcript editing. It first calls dlg2hist to group the user turns. reply2chat then parses each stored reply with msg_parts.fmt2hist and separates its tool calls and results. You can also use reply2chat on a single reply string.

The dialog must end with a prompt. dlg2chat rejects duplicate tool-call IDs, including duplicates in hand-authored replies. By default, prompts include the solveit serving envelope from task_tags. For transcript reconstruction, pass plain=True to keep the prompt’s bare content.

This conversion does not preserve every part of a stored reply. fmt2hist removes thinking blocks. reply2dlg and dlg2reply have the same limitation. Keep the original reply string if you need those blocks.

chat2dlg creates one prompt per user turn. It renders the assistant and tool messages into that prompt’s reply with hist2fmt. User images become attachments with references in the question text.

hist2fmt writes tool calls and results as fenced JSON. The round-trip checks below compare canonical messages rather than the original Markdown. Its mx limit truncates tool results and permits string arguments up to five times that length. Use mx=None to disable these limits for matched call/result pairs. Server calls without separate results still use their default display limit.

chat2dlg removes the prompt envelope and keeps the request text. An envelope’s sid restores the original message ID. Converting the reconstructed dialog back to chat then restores that ID in the envelope.

Reply sub-dialogs

A prompt stores its AI reply as Markdown with fenced JSON tool blocks. Convert legacy HTML details blocks with conv_tools before parsing them. Use reply2dlg to turn a reply into a dialog of notes and code messages. You can then edit it with the usual message operations. dlg2reply converts the edited dialog back to reply Markdown.

reply2dlg parses through fmt2hist. That parser removes token-usage and thinking blocks. When the reply ends with tool results, it adds a final . note to avoid empty assistant text. These changes also occur when converting replies to chat history.

fmt2hist retains server-tool calls. reply2dlg converts them to code messages too, but the sub-dialog does not retain their server flag.

Message.tool_call

def tool_call():

Parsed dict(name=..., arguments=...) when this code message’s source is a literal tool call, else None

For UIs and review code, tool_call reads the name and arguments without generating an ID or changing the message. It returns None for a note or source that isn’t a keyword-only call expression. Argument values must be Python literals. Nonliteral values raise during parsing:

test_eq(sub.messages[1].tool_call, dict(name='python', arguments={'code':'1+2'}))
test_eq(sub.messages[0].tool_call, None)  # a note
test_eq(Message('x = 1', msg_type=scode).tool_call, None)  # not a call expression

Parallel tool calls appear as adjacent tool blocks in a stored reply. reply2dlg makes one code message per call in document order. The final . note comes from fmt2hist. Converting this reply to a sub-dialog and back preserves the history from dlg2chat:
